# Backup and restore

What can be lost, where its copy is, and how to get it back. The design keeps
very little that needs a backup: everything in the clusters is re-created from
Git, the application is stateless, and Terraform state is versioned.

| What | Copy | Recovery |
| --- | --- | --- |
| Cluster contents (all Kubernetes objects) | Git, `k8s/` | Argo CD re-creates them ([below](#lost-cluster)) |
| AWS infrastructure | Git, `infra/` + Terraform state | re-apply |
| Terraform state | S3 object versions, 90 days | [restore a version](#terraform-state) |
| Bootstrap state (the state bucket's own state) | your copy of a local file | [import](#bootstrap-state) |
| Container images | ECR, newest 50 | revert to a kept image; rebuild otherwise |
| Secrets | Parameter Store | [regenerate or re-issue](#secrets) |
| KMS keys | 7–30 day deletion window | [cancel the deletion](#kms-keys) |
| Logs | S3 for their retention period | not backed up: telemetry |
| Grafana settings | none needed | data source provisioned from Git, no database to keep |

## Lost cluster

A broken or deleted cluster is replaced, not repaired:

1. Clean up what the old cluster's controllers left behind, if it's gone
   without a proper teardown: the ALB and target groups (tag
   `elbv2.k8s.aws/cluster`), Karpenter's instances (tag
   `karpenter.sh/nodepool`), EBS volumes and the DNS record.
2. `terraform apply` in `infra/envs/<env>`: it re-creates the cluster and
   whatever else is missing.
3. Run the Argo CD bootstrap ([cluster-bootstrap.md, step 5](cluster-bootstrap.md#5-argo-cd)).
   The parameters in Parameter Store survived, so the external-dns token
   doesn't need to be written again.
4. Argo CD rebuilds everything else from Git, in wave order.

Logs already in S3 are still there; the new Loki reads them, since the bucket
names don't change.

**Test it:** rebuilding dev from scratch with the bootstrap runbook is the
restore test. Do it after any large infrastructure change, and at least every
quarter.

## Terraform state

Each root's state is one object in the state bucket
(`envs/<env>/terraform.tfstate`, `envs/<env>/bootstrap/terraform.tfstate`,
`envs/shared/terraform.tfstate`). The bucket keeps previous versions for 90
days.

To go back to an earlier version, for example after a bad manual change or a
corrupted state, make sure nobody else is running Terraform on that root, then:

```bash
KEY=envs/dev/terraform.tfstate
aws s3api list-object-versions --bucket "$STATE_BUCKET" --prefix "$KEY" \
  --query 'Versions[].[VersionId,LastModified,Size]' --output table
aws s3api get-object --bucket "$STATE_BUCKET" --key "$KEY" \
  --version-id <version-id> restored.tfstate

cd infra/envs/dev
terraform init -backend-config="bucket=${STATE_BUCKET}"
terraform state push -force ../../../restored.tfstate   # older serial, hence -force
terraform plan                                          # shows how reality differs
rm ../../../restored.tfstate
```

The restored file contains no secrets (they're kept out of state on purpose),
but delete the local copy anyway. The plan afterwards shows what changed in
AWS since that version; apply it or import what's missing.

## Bootstrap state

`infra/bootstrap` keeps local state, because it creates the bucket every other
root uses. Keep a copy of its `terraform.tfstate` after applying it. If the
file is lost, nothing in AWS is affected; only this root can't manage the
bucket any more. Re-create the state by importing:

```bash
cd infra/bootstrap
terraform init
BUCKET="messagespring-tfstate-${ACCOUNT_ID}-ap-southeast-7"
KEY_ID=$(aws kms describe-key --key-id alias/messagespring-tfstate --query KeyMetadata.KeyId --output text)

terraform import aws_kms_key.state "$KEY_ID"
terraform import aws_kms_alias.state alias/messagespring-tfstate
for r in aws_s3_bucket aws_s3_bucket_ownership_controls aws_s3_bucket_public_access_block \
         aws_s3_bucket_versioning aws_s3_bucket_server_side_encryption_configuration \
         aws_s3_bucket_lifecycle_configuration aws_s3_bucket_policy; do
  terraform import "$r.state" "$BUCKET"
done
terraform plan    # expect no changes
```

## Secrets

Values are in Parameter Store under `/messagespring/<env>/`. External Secrets
copies them into the cluster every hour.

- **Grafana admin password:** generated by Terraform and never stored in
  state. To replace it, increase `value_wo_version` on
  `aws_ssm_parameter.grafana_admin_password` in `infra/envs/<env>/secrets.tf`
  and apply. Grafana keeps no database, so it uses the new password after its
  pod restarts.
- **Cloudflare token for external-dns:** re-issue it in Cloudflare and write it
  again ([cluster-bootstrap.md, step 4](cluster-bootstrap.md#4-the-external-dns-token)).
- **A deleted parameter:** the next `terraform apply` re-creates it (Grafana
  with a new password, the Cloudflare one with the placeholder: write the token
  again).

To make External Secrets sync now instead of within the hour:

```bash
kubectl -n logging annotate externalsecret grafana-admin force-sync="$(date +%s)" --overwrite
```

## KMS keys

Deleting a key is scheduled, not immediate: 7 days in dev, 30 in prod. Until
then it can be recovered, along with everything encrypted with it (state,
parameters, Loki chunks, EBS volumes, Kubernetes Secrets):

```bash
aws kms cancel-key-deletion --key-id <key-id>
aws kms enable-key --key-id <key-id>
```

After the window, data encrypted with the key is unrecoverable. That is why
the windows are not shorter, and why prod's is the maximum.

## Container images

ECR keeps the newest 50 images, the rollback window
([rollback.md](rollback.md)). Older images are deleted by the lifecycle
policy. To run older code, revert the code on `main` and let the pipeline
build it: a new image of old code, scanned against today's vulnerability
database.

## What is not backed up, and why

- **Logs** in S3 are telemetry with a retention period, not records. Losing
  the bucket loses history but nothing the service needs. Versioning is off on
  purpose: it would keep every chunk Loki deletes, so logs would outlive their
  retention.
- **Loki's write-ahead log** (a gp3 volume) holds the last few minutes before
  they're flushed to S3; losing the volume loses only those.

**Next step:** Velero, once something stateful runs in the clusters, to back
up persistent volumes and namespaces on a schedule.
